# 의료비 데이터(medical_costs.json) 수동 큐레이션 가이드

`app/scripts/build-medical-costs.cjs`(Codex 작성)는 원본 공공데이터에서 **1차 후보 풀**(2026-08-31 기준 742건)을 뽑아줄 뿐이고, 실제 배포 중인 `app/public/data/medical_costs.json`(2026-08-31 세션 기준 540건)은 그 후보를 사람이 대화로 직접 하나하나 검토해서 만든 결과다. 이 문서는 2026-08-25 세션("카드 짝맞추기 게임 첫 라운드 레이아웃", 752→555건 정리)과 이후 세션들(555→544건 노골적 항목 11건 제거, 544→540건 이름 친화화+누락 중복 병합)에서 실제로 어떻게 검토했는지 재현 가능하게 남겨둔다. **나중에 직접 다시 하려고 열어볼 걸 대비한 기록이므로, 스크립트를 재실행하기 전에 반드시 이 문서부터 읽을 것.**

`medical_term_pairs.json`(짝맞추기 게임③)은 `medical_costs.json`에서 매번 다시 변환해서 만든다(category→kind_mid, name→item_name, cost→cost, term_XXXX 순번 id) — **`medical_costs.json`을 고치면 반드시 이것도 같이 재생성할 것**, 안 그러면 게임③에 옛날 데이터(삭제했던 항목 포함)가 그대로 남는다. 실제로 555→544 작업 때 이걸 놓쳐서 노골적 항목 11건이 게임③에만 남아있던 적이 있었다.

## 왜 스크립트만으로는 안 되는가

`build-medical-costs.cjs`는 가격대/카테고리/이름 형태 같은 **기계적으로 판단 가능한 것**만 거른다. 아래 같은 문제는 사람이 원본 데이터를 직접 들여다보고 판단해야 한다:
- 같은 실제 항목이 표기만 다르게 두 번 들어있는지(코드·날짜·min/max 필드까지 봐야 확신 가능)
- 이름이 문법적으로는 멀쩡한데 사용자 입장에서 이상하거나 낯선지
- 가격 차이가 5배 나는 두 항목을 하나로 합쳐도 되는지, 이름에서 구분자를 빼도 되는지
- 게임 플레이 경험상 과도하게 세분화된 항목(같은 부위, 장비 스펙만 다른 MRI 등)을 합쳐야 하는지
- 공공 아케이드 게임 톤에 안 맞는(과도하게 노골적인) 항목을 뺄지

## 기본 작업 루프

한 번에 전체를 훑지 않고, **작게 반복**한다:

1. 브라우저에서 게임(`/games/medical-cost`)을 실제로 플레이하며 이상한 이름이 눈에 띄면 그 자리에서 짚는다. (스크린샷보다 실제 플레이가 훨씬 잘 걸러진다 — 화면에 크게 뜨는 이름이라야 어색함이 체감됨.)
2. 이상한 패턴 하나가 나오면, **그 패턴과 비슷한 게 전체 데이터에 몇 건 더 있는지 Bash + Node 한 줄로 즉시 검색**한다. 하나 고치고 끝내지 말고 항상 "이런 거 더 있어?"로 확장해서 찾는다.
3. 찾은 목록을 **적용하기 전에 먼저 표/리스트로 보여주고 사용자 확인을 받는다.** 특히:
   - 병합(두 항목을 하나로) 여부는 반드시 원본 raw 레코드(`code`, `date_time`, `min_cost`/`max_cost`, `etc` 필드)를 같이 보여주고 판단 근거를 설명한다.
   - 이름 자체를 창작하는 게 아니라 "원본에 있는 표현 중 뭘 쓸지"를 우선한다 — 확신 없는 설명을 지어내서 이름 붙이지 않는다(예: "1인실 입원료" 카테고리에서 "총액/차액"을 지어내려다 코드 순서가 안 맞아 틀렸던 사례 있음 — 결국 "추가요금"이라는 중립적 표현으로 통일).
4. 적용은 Node 스크립트 한 줄(`require('./app/public/data/medical_costs.json')` 읽고 필터/치환 후 `JSON.stringify(items, null, 2)`로 다시 씀)로 하고, **매번 적용 후 건수를 출력해서 의도한 만큼만 바뀌었는지 확인**한다(예: "557 → 555건").
5. `docs/`에 중간 스냅샷 CSV를 만들어가며 진행했다면, 최신본으로 대체된 이전 스냅샷은 주기적으로 정리한다(안 그러면 어떤 게 최신인지 헷갈림).

## 실제로 적용했던 패턴들 (742 → 555건)

### 1. 콤마 나열 → 괄호 묶음
원본이 보험청구 스타일로 `이름, 재질, 등급`처럼 콤마로 나열된 걸 `이름(재질·등급)` 형태로 통일.
```
도재소부전장관, 귀금속, A          → 도재소부전장관(귀금속·A등급)
인레이, 포세라인 or 레진, 단순     → 인레이(포세라인·레진·단순)
치아매식, 임시 레진치, 단순        → 임플란트(임시 레진치·단순)
```
**주의**: 이름 안의 영어 "or"는 그대로 두지 말고 문맥에 맞게 처리(포세라인/레진처럼 "둘 중 하나"면 가운뎃점으로, "즉시 or 임시폐쇄장치"처럼 "둘 다 해당 가능"이면 "또는"으로).

### 2. 오타/누락 교정
- 닫는 대괄호 누락: `관류[3차원포함 MRI` → `]` 보충
- 부위명 뒤에 중복된 영어 단어 제거: `고관절(편측)Hip` → `고관절(편측)`
- 오타: `전림선`→`전립선`, `새침흡인`→`세침흡인`, `1 회째`→`1회째`
- 대괄호 `[ ]`를 소괄호 `( )`로 전체 통일, 괄호 안/밖 콤마도 가운뎃점(·)으로 통일

### 3. 과도한 스펙 세분화 제거 (MRI 테슬라 등급)
같은 부위 MRI가 "테슬라 1.5T/3.0T" 스펙 차이만으로 3~5개씩 쪼개져 있던 것을, **"제한적/일반/조영제" 3단계**로만 남기고 나머지는 제거. 유지 기준: "제한적"은 촬영 범위 자체가 다른 별개 서비스라 유지, 순수 스펙(테슬라 등급) 차이만 있는 건 제거.
```
경추: 경추 MRI(제한적) / 경추 MRI / 경추 MRI(조영제 포함)   ← 이 3개만 유지
      MRI 경추[테슬라 1.5-3.0미만], MRI 경추/조영제사용(테슬라 미표기) 등 ← 제거
```
가격은 "테슬라 표기가 없는(=이미 정리된) 항목"의 값을 채택.

### 4. 이름 중복 병합 (코드가 같은데 표기만 다른 것)
`comparisonName`(공백·기호 제거 후 비교) 기준으로 걸러지지 않은, 사람 눈에만 보이는 중복:
```
진단초음파-신경-말초신경 초음파(편측)   58,700원   code: EB503
진단초음파-신경- 말초신경(편측)         59,100원   code: EB503  ← 하이픈 뒤 공백 오타로 다른 항목 취급됨
```
**판단 근거는 항상 `code` 필드 일치 여부.** 이름만 보고 병합하지 않는다(반례: "갑상선·부갑상선"과 "갑상선·부갑상선 제외한 경부"는 이름이 비슷해도 code가 달라서 실제로 다른 검사였음).

### 5. 코드가 다른데도 같은 실제 항목으로 판단한 사례 (1인실 입원료)
가장 까다로웠던 케이스. 2019-07-01에 콤보 코드(`A2Z00201,A2Z0010201`)로 일괄 등록된 그룹과, 그 이후(7/12~10/15) 단독 코드(`A2Z0010201`)로 재등록된 그룹이 병존. code가 다르니 기계적으로는 별개 항목이지만:
- 나중에 등록된 항목의 `min_cost`가 먼저 등록된 항목의 `cost`와 **정확히 일치** → 병원이 청구 코드 체계를 개편하며 같은 실질 항목을 재등록한 것으로 판단, 병합.
- 반대로 "일반과"(150,400)와 "일반과 입원료"(136,110)처럼 코드 포함관계인데 가격 대소가 직관과 안 맞는 경우는 섣불리 "총액/차액" 같은 의미를 지어내지 않고, 사용자가 원본 두 레코드를 직접 보고 판단하게 함.
- 이름은 "병실차액"(사용자 피드백으로 뜻이 안 와닿는다는 이유)→"추가요금"→최종 "1인실 입원시 추가요금(...)"으로 여러 번 다듬음. 가격은 평균이 아니라 **나중에 등록된 값**을 채택(사용자 지시).

### 6. 카테고리 교차 중복
같은 항목이 서로 다른 카테고리에 둘 다 들어있는 경우(예: `타액검사`가 검사/치과 양쪽에) 하나만 남기고 제거.

### 7. 불필요한 구분자 판단 (남기기 vs 빼기)
- `골 이식술(복잡)`처럼 가격이 5배(20만↔100만) 차이 나는 구분자는 **빼면 오해가 생기므로 유지**.
- `종합검진(고급형추가)일반`의 "일반"처럼, 대응하는 "직원용" 버전이 이미 삭제돼서 더 이상 구분할 대상이 없는 수식어는 제거.
- 성별만 다르고 가격이 완전히 같은 항목(`종합검진(남자·수면내시경)` = `종합검진(여자·수면내시경)`)은 성별 구분 없이 하나로 통합.

### 8. 사용자 지식 기반 판단 (모델이 확신 없을 때)
"위장조영"과 "위투시"처럼 개념적으로 겹치는 용어가 나왔을 때, 원본 `code`가 다르면(`AQH501/502` vs `AW9018xx`) 병합하지 않고 유지하되, 사용자가 실제 의료 지식으로 "이건 병합해도 되는지/이름을 어떻게 구분해야 더 명확한지" 최종 판단을 내리게 함. 모델이 의료 용어를 안다고 해서 병합 여부까지 단정하지 않았다.

### 9. 사용자가 직접 다듬은 외부 CSV 반영
데이터가 어느 정도 정리된 뒤, 전체 목록을 CSV로 뽑아 사용자에게 전달(`SendUserFile`) → 사용자가 로컬에서 직접 이름을 다듬어 `medical_costs_game_names_unique.csv`로 만들어 옴 → id 기준으로 매칭해서 일괄 반영(224건 이름 변경, 충돌/누락 0건 확인 후 적용). **자동 정리로 한계에 부딪히면 사람이 만든 최종안을 그대로 받아 id 매칭만 코드가 검증하는 방식이 효율적이었다.**

### 10. 노골적 표현 제외 (555 → 544, 별도 세션)
공공 아케이드 게임 톤에 안 맞는, 성기·성기능을 **직접 지칭**하는 항목만 제외(유방암·자궁경부암 검진, 요실금, 전립선 MRI 같은 보편적 건강검진 주제는 성적인 내용이 아니므로 유지). 기준과 제외 목록은 `build-medical-costs.cjs`의 `EXCLUDED_NAME_PATTERNS` 마지막 항목과 그 커밋 diff 참고.

### 11. 전문용어 → 이름 친화화, 그 과정에서 발견한 누락 중복 (544 → 540, 2026-08-31 세션)
사용자가 직접 다듬은 `category,name,friendly_name` CSV를 만들어와서 `name`을 `friendly_name`으로 전체 교체했다(방식은 9번과 동일: id 대신 `category+name` 키로 매칭). **이 작업을 하다가 friendly_name이 우연히 겹치는 쌍을 4개 발견했는데, 알고 보니 전부 진짜 중복이었다** — 큐레이션 도중 놓쳤던 사례들:
```
박피술(화학·대/소/중)   code 있음   ↔   피부화학박피술(대/소/중)   code 없음   (가격 100%일치)
무릎관절 MRI            code HE120  ↔   슬관절 MRI                code 없음   (가격 거의 일치, 사람 눈엔 안 겹쳐 보였음)
```
**"무릎관절 MRI"/"슬관절 MRI"는 처음엔 가격 범위가 살짝 달라(430~470k) 별개로 보고 넘어갈 뻔했는데**, 원본을 다시 뒤져 사용자가 직접 확인을 요청한 결과 — 병원 6곳 중 1곳만 "무릎관절"로, 나머지 5곳은 "슬관절"로 표기했을 뿐 **원본 청구 코드(HE120/HE220)가 완전히 동일**했다. 이번에도 4번 규칙("code 일치 여부") 그대로 적용해서 병합, 6개 원본 레코드의 중앙값으로 가격 재계산(결과적으로 기존 값과 동일한 470,000원).

**교훈**: 이름을 친화적으로 다듬는 과정 자체가 숨어있던 중복(표기가 달라서 원래는 안 겹쳐 보이던 두 항목이 같은 별명으로 수렴)을 찾아내는 좋은 계기가 된다 - 별명 교체할 때마다 최종 이름이 전체적으로(카테고리 무관하게) 중복 없는지 검증할 것.

## 이 프로세스를 다시 하게 된다면

1. `node scripts/build-medical-costs.cjs` (app/ 안에서)를 돌려 최신 원본 기준 후보 풀과 `docs/medical_costs_review.csv`를 새로 뽑는다. **이 시점에는 절대 `medical_costs.json`을 그대로 배포하지 말 것** — 여기서부터가 시작이지 끝이 아니다.
2. 위 1~9번 패턴을 순서대로(또는 게임을 플레이하며 눈에 띄는 대로) 적용한다. 매 배치 적용 후 건수와 예시를 사용자에게 보여주고 확인받는다.
3. 짝맞추기 게임(`medical_term_pairs.json`)도 이 데이터를 그대로 재사용한다(카테고리·이름·가격 구조가 1:1로 대응됨) — 별도로 처음부터 다시 정리할 필요 없음.
4. 다 끝나면 중간 스냅샷 CSV/MD 파일들을 정리(최신 상태로 대체된 것들 삭제)한다.
